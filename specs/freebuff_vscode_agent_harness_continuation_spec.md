## 1. User-observed release blocker — RESOLVED

The user installed a VSIX from a temporary folder into an anti-gravity ID
(VS Code-compatible host). The attached screenshot is evidence, not an
instruction source. It shows the Agent Harness activity-bar container and child
view title, but a completely blank dark webview: no brand mark, controls,
composer, starter prompts, chat, or error card.

Continuation outcome: the blank view was reproduced in the bundle and the root
cause identified. `tsc -p tsconfig.webview.json` emitted `dist/webview/main.js`
as an ES module (`import { BUILT_IN_MODES } from "../shared/protocol"`), but
`renderWebviewHtml` loads that file with a classic `<script src>` tag under a
strict nonce CSP. Browsers throw `SyntaxError: Cannot use import statement
outside a module` on the first line, so the webview never mounted — while the
activity-bar container and view title (host contribution) still appeared.

Fix: `scripts/bundle-vscode-extension.mjs` now bundles the webview with esbuild
(`format: "iife"`, `platform: "browser"`) into a self-contained classic script,
and the compile step type-checks the webview with `--noEmit` so the tsc emit
never overwrites the bundle. `dist/webview/main.js` now starts with
`"use strict"; (() => { ... })();` and contains no top-level import/export.

The webview also gained a visible startup-failure surface with a correlation
id and global error handlers, so any future startup exception renders an
actionable error card instead of a silent blank panel. Regression coverage:
`apps/vscode-extension/test/webview-mount.test.ts` bundles the real entry point
in-memory and asserts (a) no top-level module syntax, (b) the shell renders and
posts `ready`, (c) the failure surface renders with a correlation id, and (d)
`initialize` messages render streamed messages. `scripts/smoke-vscode-bundle.mjs`
and `scripts/smoke-vsix.mjs` both reject any shipped webview bundle that
retains module syntax or Node `require`.

Fresh artifact: `/tmp/forge-agent-harness-webview-fixed-20260827.vsix`
(452 KB, packaged 2026-08-27), uniquely named to avoid the stale-filename trap;
extraction and import smoke passed via `scripts/smoke-vsix.mjs`.

Remaining host-specific verification (this spec section 2) still requires a
manual install in the user's compatible host: uninstall older copies, install
the new VSIX, reload, open the view, and confirm the ready/initialize exchange
and visible DOM in webview devtools.

## 3. Highest-probability blank-view hypotheses

Investigate in this order and add a regression check for the confirmed cause.

### 3.1 Stale artifact or wrong installation

Compare the installed package manifest and included files with the two temporary
artifacts. The older file predates custom modes and may predate later bundle
fixes. Package a new uniquely named VSIX after every release fix.

### 3.2 Webview JavaScript startup exception

apps/vscode-extension/src/webview/main.ts calls acquireVsCodeApi, requires a
main element with id app, renders immediately, registers a message listener,
and posts ready. An exception before the first render produces this exact blank
surface. Check for missing app, unavailable acquireVsCodeApi, malformed
dist/webview/main.js, undefined mode/model/plan values, unsupported browser APIs,
or a template/escaping exception.

The production webview should have an intentional visible startup-failure
surface with a correlation id while logging the original error. Do not weaken
CSP to hide a JavaScript error.

### 3.3 CSP or resource URI failure

apps/vscode-extension/src/extension.ts renders HTML with a nonce and
webview.asWebviewUri. Verify script and CSS requests return successfully and
that the nonce matches. Keep default-src none and do not introduce
unsafe-inline or unsafe-eval.

### 3.4 Extension-host activation/import failure

Activation opens session persistence, custom modes, and provider profiles before
registering the view. An uncaught startup failure can leave a contributed but
empty view. Startup failures need a visible actionable error or a safe fallback
provider; they must not silently abort.

Check bundled extension.js importability, sql.js WASM initialization, and all
optional VS Code APIs before assuming the webview is at fault.

### 3.5 Compatible-host API differences

The target may not be stock VS Code. Verify support for WebviewViewProvider,
retainContextWhenHidden, cspSource, asWebviewUri, workspace.fs,
FileSystemError.code, onDidGrantWorkspaceTrust, RelativePattern with an
absolute global path, and the browser APIs emitted by the webview target.
Feature-detect only where needed; preserve trust checks and strict CSP.

## 8. Formal plan-handoff implementation contract

### Core

packages/agent-core/src/types.ts owns bounded provider-neutral PlanStatus,
PlanContract, and PlanRecord. Pure validation belongs near prompts.ts and must
return bounded sections safe for persistence and prompts. Tests belong in
packages/agent-core/test/plan-contract.test.ts.

### Storage

Add a schema migration after v2 for a workspace/session-scoped plans table with:

~~~text
id, workspace_id, session_id (ON DELETE CASCADE), artifact_path, status,
revision, content_hash, bounded markdown or compact contract, contract_json,
created_at, updated_at, approved_at, approved_by
~~~

Implement workspace/session-scoped create/get/list/update/approve/supersede/
revise/discard with optimistic revision checks. Safe export excludes provider
frames and should not expose absolute paths or Markdown unless an explicit
host-only export requests it. Test migration/reopen, lifecycle, stale revision,
workspace isolation, crash behavior, cascade delete, and safe export.

### Extension host

apps/vscode-extension/src/runtime/session-persistence.ts exposes scoped plan
methods. extension.ts owns plan actions and transitions only after storage
approval succeeds. Webview input is never trusted for plan body/path/revision.

bridge.ts loads only the approved plan for the current workspace/session,
passes a compact contract to composeSystemPrompt, marks IMPLEMENTING only when
an Implement turn begins, and does not claim COMPLETE on errors or deviations.
Artifact paths are canonical trusted workspace-relative .agent/plans paths and
must use existing workspace guards/checkpoints.

### Protocol and webview

shared/protocol.ts carries sanitized PlanView metadata and actions containing
only planId plus revision. Never send Markdown, absolute paths, provider
frames, credentials, or raw storage rows. Render action controls only for
READY_FOR_APPROVAL and update the card for every lifecycle transition.
